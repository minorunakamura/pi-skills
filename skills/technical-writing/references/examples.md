# 具体例と確認観点

以下は表現と判断の境界を確認するための例。記載した動作は、対象の仕様や資料に根拠がある場合にだけ書く。
Skill を変更したときは、各例の「確認」を満たすか手動で見直す。文言の完全一致ではなく、意味が保たれることを確認する。

## 1. 抽象語を、根拠のある動作として説明する

原文：

> 受付と完了確認を分離する。

提供資料：API は Job を受け付けると Job ID を返す。クライアントは Job ID を使って状態を問い合わせる。受付時には処理の完了を待たない。

書き換え例：

> API は処理の完了を待たずに、受付結果として Job ID を返す。クライアントは、その Job ID を使って処理の状態を問い合わせる。

確認：提供資料にある役割と動作を説明できていること。再試行、通知、保存方法など、資料にない仕組みを追加しないこと。
資料がなく原文だけの場合は、応答や確認の方法を決めず、不足情報として確認すること。

## 2. 条件、否定、許可を保つ

原文：

> 管理者は、処理中の Job を削除してはならない。完了済みの Job は削除してよい。

書き換え例：

> 管理者は、完了済みの Job を削除してよい。処理中の Job は削除してはならない。

確認：削除の許可と禁止、対象者、Job の状態が同じであること。
「削除できる」は機能や権限の説明にも読めるため、許可の言い換えとして使わないこと。削除ボタンの無効化や API のエラー応答を勝手に追加しないこと。

## 3. 未確認を決定や保証に変えない

原文：

> 完了通知はメールを候補とする。配信サービスの選定と再送の要否は未決定。通知の遅延は未計測。

書き換え例：

> 完了通知の手段としてメールを検討している。配信サービスと、再送を行うかどうかは決まっていない。通知の遅延は、まだ計測していない。

確認：メールの採用、再送、配信時間を確定しないこと。計測していないことを、遅延が大きい・小さいという評価に変えないこと。

## 4. 数値と例外の適用範囲を保つ

原文：

> 1回のリクエストで最大100件を受け付ける。ただし管理者による実行では最大500件とする。失敗した項目だけを再実行する。

書き換え例：

> 1回のリクエストで受け付ける件数は、通常は最大100件、管理者が実行する場合は最大500件とする。失敗した項目だけを再実行する。

確認：上限が1回のリクエスト当たりであること、管理者の例外、失敗項目への限定を保つこと。自動再試行、回数上限、リクエスト全体の再実行を追加しないこと。

## 5. 曖昧さを推測で解消しない

原文：

> Worker が失敗したら、それを保存して再実行する。

対応例：

> 「それ」が指す保存対象と、再実行の対象を確認する。Job、入力、エラー情報などのどれを指すかは、この文だけでは確定しない。

確認：まず前後や資料を調べ、確定できなければ必要な点だけを質問すること。Job やエラー情報を推測で選んで本文を書き換えないこと。

## 6. 正確で自然な要求文は残す

原文：

> API は、存在しない Job ID に対して HTTP 404 を返す。

対応例：変更しない。

確認：すでに主体、条件、結果が明確な文を、推敲のためだけに長くしないこと。HTTP 404 を別の状態やエラー形式に変えないこと。
