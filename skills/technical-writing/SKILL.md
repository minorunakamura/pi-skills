# Technical Writing

仕様書、設計書、Plan、Work Item などの日本語の技術文書を作成・推敲する。
まず読み手に伝わる説明を組み立て、その後で意味を保ちながら簡潔にする。文字数の少なさより、読み違えずに理解できることを優先する。

## 担当範囲

- 文書に必要な内容、詳細度、形式、保存先は、ユーザーの依頼、プロジェクトの規約、呼び出し元の Skill に従う。設計書を詳細な実装計画に変えるなど、文書の役割を変えない。
- 説明の順序、文や段落の構造、日本語の表現を整える。仕様の決定、設計の採否、合意・承認の判定は担当しない。
- 他の Skill から使う場合は、その文書作成・更新の手順内でこの Skill を読み、執筆方針として適用する。別 Agent や追加の承認工程は不要。
- 相談・レビューでは提案までにとどめる。編集を依頼された場合だけ指定範囲を変更し、呼び出し元の保存・承認・公開ルールを維持する。承認済みの文書も、無断で書き換えない。
- 通常の短い会話や作業報告、誤字だけの修正、コードの書き換えには一律に適用しない。

## 1. 読み手・目的・根拠を確認する

対象の文書と理解に必要な前後の文脈、提供された資料を読む。図表が説明の一部なら、それも確認する。
読み手が何を理解・判断・実行するための文書かを把握する。既存の文体、用語、識別子、参照先を確認する。

既存文の推敲では、原文の主張と、資料に照らして確認が必要な箇所を区別する。
新規作成では、依頼・確認済み資料・合意した内容を根拠に書く。資料の短い表現を、そのまま説明として写す必要はない。
根拠のない担当、動作、理由、条件、数値を補わない。資料間の矛盾や意味の曖昧さは、表現の調整だけで解決したことにしない。

## 2. 先に説明を組み立てる

文字数を削る前に、読み手が隣にいるつもりで「何がどうなるか」「なぜそうするか」「どんな場合か」を必要な範囲で説明する。
完成文は口語に統一せず、文書の目的と既存の文体に合わせる。説明用の下書きや検討過程を出力する必要はない。

- 冒頭で、その文書が扱う課題や変更の全体像を伝える。既存のテンプレートがあれば、その構成の中で説明する。
- 「分離」「管理」「対応」「保証」などの抽象語だけで動作の説明を終えない。根拠がある範囲で、主体、対象、動作、結果を示す。理由が不明なら作り足さない。
- 全体像から役割や流れ、必要な条件へと、理解に必要な順序で説明する。すべての文書に同じ見出しや順番を強制しない。
- 仕組み、採用理由、条件、例外は話を分ける。条件や例外は、対応する動作や判断の近くに置く。
- 概要や理由は文章で、独立した要求や手順は箇条書きで、状態・値・条件の対応は必要に応じて表や図で示す。仕様全体を散文に変えない。
- 必要な専門用語は保ち、読み手に必要なら初出で意味を添える。同じ対象を別の名前で呼ばない。

## 3. 意味を保って簡潔にする

重複、内容のない前置き、不要な装飾を削る。読み手が前の文に戻らず理解できるように、主述・修飾・指示語の対応を整える。

- 名詞を詰めた短句より、対象と動作が分かる文を選ぶ。長い文は、条件・否定・因果関係が掛かる範囲を保って分ける。
- 「これ」「その処理」などの指す先が不明瞭なら、根拠から特定できる場合だけ対象名を書く。
- 不自然な比喩は具体的な表現にする。ただし、定義済みの専門用語や、システムの客観的な動作を述べる表現は無理に言い換えない。
- 主体や関係が明らかな自然な文は残す。すべての文に主語を足したり、文長・読点数・箇条書き比率を機械的に揃えたりしない。
- 操作の案内は、読み手が何をすればよいかを直接書く。禁止、対象外、例外、安全上の注意など、否定に意味がある箇所は保つ。
- 短くすると重要な条件や理由が失われるなら、必要な言葉を戻す。指定の長さに収まらない場合は、意味を削らず、長さや構成の調整を提案する。

## 4. 仕様と判断の意味を照合する

推敲後は原文と、新規作成後は根拠資料と読み比べる。読みやすさだけで完了とせず、次が変わっていないか確認する。

| 確認対象 | 保持する内容 |
| --- | --- |
| 主体・対象・動作 | 誰が何に何をするか。実行、待機、通知などの担当 |
| 条件・数量・順序 | 条件と例外の適用先、すべて／いずれか、上限、単位、処理順 |
| 否定・義務・許可・能力 | しない／失敗する、してはならない／しなくてもよい、する／してよい／できる |
| 確実性・時制 | 必ず／場合がある、事実／推測、現在の動作／将来の予定／実施済み |
| 判断の状態 | 決定／提案／仮定／保留／未確認、合意・承認の対象と範囲 |
| 主張・理由・比重 | 因果関係、比較対象、推奨の強さ、重要な制約や不利益 |
| 技術的な値と参照 | 識別子、API、コード、数値、エラー、リンク先を維持しているか |

公式用語や識別子は、本文だけでなく表・図・注記でも一致させる。
原文の誤りが疑われる場合も、黙って仕様を変更しない。問題と修正案を示し、必要な調査や判断はユーザーまたは呼び出し元の手順に戻す。
文書だけで主要な動作と条件を理解できるかも確認する。曖昧さが残るなら単語の置換を繰り返さず、説明の組み立てか不足情報の確認に戻る。

条件や判断の状態を含む文の推敲、または意味を保てるか迷う場合は、[具体例と確認観点](references/examples.md)を読む。例の動作を、対象文書の仕様として流用しない。
この照合は仕様の正しさや網羅性を保証する検証ではない。

## 不足情報と出力

- 意味が複数に取れる場合は、まず前後や資料を確認する。それでも決まらなければ、判断に影響する点だけを質問する。未確定のまま文書に残す場合は、その状態を明示する。
- 通常は完成した本文を先に示し、必要な変更理由や確認事項を本文の後に分ける。呼び出し元が Plan 全文などの形式を定めている場合は、その形式を守る。
- 推敲上の確認事項を仕様として本文に混ぜない。ただし、文書に残すべき既存の未決事項やリスクは省略しない。
- ファイルを編集した場合は保存結果を読み直し、本文・表・参照の整合を確認する。既存のユーザー変更を保持する。保存や表示を確認できなければ、確認できた範囲を区別して報告する。
- Review に提出する本文と保存する本文を、別の仕様として管理しない。承認後の変更が必要なら呼び出し元の再承認手順に従う。
